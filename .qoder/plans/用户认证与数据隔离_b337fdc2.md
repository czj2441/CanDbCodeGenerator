# 用户认证与数据隔离实施方案

## 需求确认

| 维度 | 决策 |
|------|------|
| 部署场景 | 小团队局域网（2-5人） |
| 认证方式 | 用户名 + 密码，配置文件存储 |
| 管理员 | 配置文件中指定 role=admin。Admin **不能直接写非自己拥有的文件**，需先通过"转移所有权"接管文件后才可写。Admin 不能删除/降级自己（防止无 admin）。支持热重载（验证后生效，有误则拒绝并维持旧配置）。启动时配置有误则阻塞启动 |
| Token | 后端生成随机 token（`secrets.token_hex(32)`）存服务端内存 dict：`{token: {username, expires_at}}`。前端存入 `localStorage['canmatrix_auth_token']`，每次请求时读取并附在 `Authorization: Bearer <token>` 头中。后端收到后从内存 dict 反查用户身份 + 滑动续期 |
| 密码存储 | SHA-256 + salt |
| 数据隔离 | 共享目录 + 权限标记（创建者=所有者）。**只有 owner 可写**，非 owner（包括 admin）只读。无 `.perm.json` 的文件**全员只读**，admin 可通过"转移所有权"接管 |
| 登录UI | 独立登录页，未登录不可访问任何功能 |
| 只读行为 | 可查看 + 导出 + **另存为**（创建自己的副本），不可编辑 |
| 文件可见性 | **默认只显示当前用户拥有的文件**，可切换显示全部文件。所有文件带权限标记（所有者/只读） |
| 文件创建 | 所有已登录用户均可创建新文件，创建者自动成为 owner |
| import_file | 仅允许创建新文件，不允许覆盖已有文件 |
| steal_lock | 仅文件 owner 可执行（admin 需先接管） |
| change_file_owner | 仅 admin 可执行（用于转移任意文件的所有权，含接管无主文件） |
| 删除用户 | 用户名下有文件时拒绝删除，需先转移所有权。不能删除/降级最后一个 admin |
| 所有权变更 | 不影响当前编辑会话。当前编辑者继续持有锁直到主动释放或超时 |

## 设计原则

1. **零 handler 修改**：通过 Router 层拦截器 + data dict 注入 username，30+ 个现有 handler 无需改动
2. **强制认证**：`users.json` 不存在时自动生成默认模板（含 admin/admin 账号），首次登录后强制修改密码。配置加载前必须通过 schema 验证，启动时验证失败则阻塞启动；运行时热重载验证失败则 console 报错并拒绝加载，维持内存中的旧配置
3. **集中鉴权**：HTTP 中间件 + WS 握手 + Router 拦截器三个点覆盖所有入口
4. **后端权威**：UI 只读控制仅为体验优化，权限强制在后端执行
5. **严格所有权**：只有文件 owner 可写，admin 无特权写入（需先接管）。这是与常见 RBAC 模型的关键区别

## 实施步骤

### 阶段 1：后端认证核心（新建文件，零侵入）

#### Step 1: 创建 AuthService

**新建** `app/auth/__init__.py`（导出）
**新建** `app/auth/service.py`（~220 行）

职责：用户管理 + Token 管理 + 文件所有权，合并为单一服务类。

**用户配置** — 读取 `config/users.json`：
```json
{
  "users": [
    {"username": "admin", "password_hash": "sha256_hex", "salt": "hex16", "role": "admin"},
    {"username": "alice", "password_hash": "sha256_hex", "salt": "hex16", "role": "user"}
  ],
  "token_ttl_hours": 8
}
```

**核心 API**：
- `is_enabled() -> bool` — 始终返回 True（认证强制启用）
- `verify_password(username, password) -> dict | None` — 验证密码，返回 `{username, role}`
- `create_token(username) -> str` — `secrets.token_hex(32)`，存内存 dict
- `validate_token(token) -> dict | None` — 验证 + **滑动续期**（每次验证延长 expires_at）。同时检查用户是否仍存在于用户数据库中（删除用户后 token 立即失效）
- `revoke_token(token)` — 登出
- `revoke_user_tokens(username)` — 删除用户时立即失效其所有 token
- `is_admin(username) -> bool`
- `reload_config() -> bool` — 热重载配置文件（由 watchdog 文件监听触发）：先读取并验证新文件 → 验证通过则替换内存数据并返回 True → 验证失败则 console 报错、拒绝加载、维持旧配置并返回 False
- `cleanup_expired()` — 清理过期 token（由心跳定时器附带调用）
- `get_file_permission(file_name) -> dict | None` — 读取 `data/{file_name}.perm.json` 权限侧车文件
- `set_file_permission(file_name, owner, **kwargs)` — 创建/更新权限侧车文件
- `remove_file_permission(file_name)` — 删除文件时移除权限侧车文件
- `can_write(file_name, username) -> bool` — **严格所有权**：有 `.perm.json` 时仅 owner 返回 True；无 `.perm.json` 时返回 False（全员只读，含 admin）
- `is_owner(file_name, username) -> bool` — 判断用户是否为文件 owner（有 `.perm.json` 且 owner 匹配）
- `has_user_files(username) -> bool` — 检查用户名下是否有文件（用于删除用户前的安全检查）
- `list_users() -> list[dict]` — 列出所有用户信息
- `create_user(username, password, role) -> dict` — 创建用户（自动设置 `must_change_password: true`），写入 users.json
- `delete_user(username, operator) -> dict` — 删除用户。**安全检查**：①有文件则拒绝（返回错误 + 文件列表）；②是最后一个 admin 则拒绝。通过后立即失效该用户所有 token
- `update_user_role(username, role, operator) -> dict` — 修改用户角色。**安全检查**：降级 admin 时检查是否为最后一个 admin，是则拒绝
- `reset_user_password(username, new_password) -> bool` — 管理员重置用户密码
- `count_admins() -> int` — 统计当前 admin 数量（用于安全检查）

**权限侧车文件格式** — 每个数据文件对应一个独立的权限 JSON 文件：

数据文件：`data/project.properties`
权限文件：`data/project.properties.perm.json`
```json
{
  "owner": "alice",
  "created_at": 1723456789.0
}
```
> 每个文件独立管理权限，删除数据文件时必须同步删除对应的 `.perm.json`。**无权限文件的文件全员只读（含 admin）**。Admin 可通过右键菜单"转移所有权"接管无主文件（创建 `.perm.json` 并设自己为 owner）。

**配置缺失处理**：`users.json` 不存在 → 自动生成 `config/users.json.default` 模板（含 `admin/admin` 账号 + `must_change_password: true` 标记）→ 首次登录后强制修改密码。

**配置验证**：启动时调用 `_validate_config(data) -> list[str]` 检查 JSON schema（用户名非空、role 合法、password_hash 格式正确、至少一个 admin 账号等）。验证失败 → 打印错误列表到 console → 阻塞启动（抛出异常）。

**热重载**：通过 watchdog 库监听 `config/users.json` 文件 mtime 变化事件，检测到变化时自动触发 `reload_config()`：读取新文件 → 验证 → 通过则原子替换内存数据 → 失败则 console 报错，维持旧配置不变。不提供 REST API 端点。

**首次登录强制改密**：`users.json` 中用户可设置 `must_change_password: true`，登录成功后后端返回标记，前端弹出修改密码对话框，未修改前不可进入主界面。

**Token 存储**：`_tokens: dict[str, dict]` = `{token: {username, expires_at}}`，服务端内存，重启后 token 失效（用户重新登录，LAN 小团队可接受）。

**线程安全**：用户数据加载后不可变（read-only），热重载时通过原子替换引用（`self._users = new_users`）更新。Token dict 用 `threading.Lock` 保护。

#### Step 3: HTTP 认证端点 + 中间件

**修改** `app/server/http_handler.py`

1. **新增模块级变量**（仿照 `SESSION_MGR` 模式，~L21 附近）：

   - `DELETE /api/admin/users/{username}` — 删除用户 + 立即失效所有 token（**有文件则返回 409 + 文件列表；最后一个 admin 则返回 409**）
   - `PUT /api/admin/users/{username}/role` — 修改用户角色（**降级最后一个 admin 返回 409**）
   - `PUT /api/admin/users/{username}/password` — 管理员重置用户密码
   - `PUT /api/admin/file-permission` — 转移文件所有权 / 接管无主文件（`{file_name, new_owner}`）

5. **新增通用端点**：
   - `GET /api/file-permission?file=xxx` — 获取文件所有者信息（登录用户均可访问）

6. **白名单**（无需认证的路径）：
   - `/api/status`、`/api/version` — 健康检查/版本（登录前需要）
   - `/api/login` — 登录本身
   - `/api/export` — 导出（仅验证 session_id，不额外鉴权，浏览器下载无法携带 Authorization 头，所有登录用户均可导出）
   - `/api/release` — 文件锁释放（sendBeacon 场景）
   - 静态文件 — 前端 SPA 资源（路由守卫在前端做）

   token = msg.get("token", "")

#### Step 5: Router 权限拦截器

**修改** `app/ws/router.py`

1. **新增模块级常量**：
   ```python
   # 需要写权限的操作（仅文件 owner 可执行）
   WRITE_OPERATIONS = frozenset({
       'edit_signal', 'add_signal', 'delete_signal',
       'batch_add_signals', 'batch_edit_signals', 'batch_delete_signals',
       'edit_message', 'add_message', 'delete_message',
       'batch_edit_messages', 'batch_delete_messages',
       'edit_database', 'undo', 'redo', 'save',
       'delete_file',
       'add_value_table', 'update_value_table', 'delete_value_table', 'rename_value_table',
   })
   # 文件创建操作（任何登录用户均可，创建后自动设 owner）
   FILE_CREATE_TYPES = frozenset({'new_file', 'create_file'})
   # 文件导入（仅创建新文件，不允许覆盖已有文件）
   FILE_IMPORT_TYPES = frozenset({'import_file'})
   # 免除写权限检查的操作
   WRITE_EXEMPT = frozenset({'save_as'})
   # 仅 admin 可执行的操作
   ADMIN_ONLY_OPERATIONS = frozenset({'change_file_owner'})
   # 仅 owner 可执行的操作
   OWNER_ONLY_OPERATIONS = frozenset({'steal_lock'})
   ```

2. **dispatch() 方法修改**（~L59-107）：
   - 在 handler 执行前插入权限检查
   - 从 `data["_username"]` 获取用户名
   - **写操作检查**：msg_type 在 WRITE_OPERATIONS 中 → 调用 `auth.can_write(file_name, username)`，仅 owner 返回 True
   - **admin-only 检查**：msg_type 在 ADMIN_ONLY_OPERATIONS 中 → 验证 `auth.is_admin(username)`
   - **owner-only 检查**：msg_type 在 OWNER_ONLY_OPERATIONS 中 → 验证 `auth.is_owner(file_name, username)`
   - **save_as 免除检查**：msg_type 在 WRITE_EXEMPT 中 → 跳过写权限检查（任何用户均可另存为）
   - **import_file 限制**：msg_type 在 FILE_IMPORT_TYPES 中 → 仅允许创建新文件，如目标文件已存在则拒绝
   - **文件创建后设 owner**：handler 执行成功后，如果是 FILE_CREATE_TYPES 或 FILE_IMPORT_TYPES → 调用 `auth.set_file_permission(file_name, owner=username)`
   - **权限拒绝响应**：返回 `HandlerError("permission_denied", ...)` 并携带当前文件 owner 信息

3. **构造函数扩展**：接受可选的 `auth_service` 参数

#### Step 7: 前端 Auth Store

**新建** `frontend/src/stores/authStore.js`（~90 行）

```javascript
export const useAuthStore = defineStore('auth', {
  state: () => ({
    token: localStorage.getItem('canmatrix_auth_token') || '',
    username: '',
    role: '',          // 'admin' | 'user' | ''
    authMustChangePassword: false, // 当前用户是否需要强制改密
  }),
  getters: {
    isLoggedIn: (state) => !!state.token,
    isAdmin: (state) => state.role === 'admin',
  },
  actions: {
    async login(username, password) { ... },        // POST /api/login
    async logout() { ... },                           // POST /api/logout + clearAuth
    async checkSession() { ... },                     // GET /api/me 验证 token
    async changePassword(oldPwd, newPwd) { ... },     // POST /api/change-password
    setAuth(token, username, role) { ... },            // 存 localStorage
    clearAuth() { ... },                               // 清 localStorage
    // ── 管理员操作 ──
    async fetchUsers() { ... },                        // GET /api/admin/users
    async createUser(username, password, role) { ... }, // POST /api/admin/users
    async deleteUser(username) { ... },                 // DELETE /api/admin/users/{username}（有文件返回 409 + 文件列表）
    async updateUserRole(username, role) { ... },      // PUT /api/admin/users/{username}/role（最后 admin 降级返回 409）
    async resetUserPassword(username, password) { ... }, // PUT /api/admin/users/{username}/password
    async changeFileOwner(fileName, newOwner) { ... },  // PUT /api/admin/file-permission（含接管无主文件）
  }
})
```

## 风险与缓解

| 风险 | 缓解策略 |
|------|---------|
| WS 认证绕过 | hello 握手必须验证 token，无 token 直接 `ws.close(4010)` |
| `sendBeacon` 无法携带 Auth 头 | `/api/release` 不鉴权（安全幂等操作） |
| 配置文件不存在 | 自动生成默认模板（admin/admin），首次登录强制改密 |
| 配置文件热重载验证失败 | watchdog 检测文件变化后验证，失败则 console 打印错误详情，拒绝加载新配置，维持内存中的旧配置 |
| 首次登录默认密码未修改 | `must_change_password` 标记强制改密，未改密前不可进入主界面 |
| Token 仅存内存，重启需重新登录 | LAN 小团队可接受 |
| 文件权限侧车文件不同步 | 无 `.perm.json` 的文件全员只读（含 admin）；删除文件时同步删除侧车文件 |
| Router 拦截器遗漏新写操作类型 | 采用"读操作白名单 + 默认需要认证"策略 |
| 多标签页 Token 共享 vs Session 独立 | auth token 在 localStorage（身份），session_id 在 sessionStorage（会话）— 正确设计 |
| LAN 部署 Token 明文传输 | LAN 可信环境；可后续升级 HTTPS/WSS |
| 删除活跃用户 | 删除用户后立即失效其所有 token，下次请求返回认证失败，前端自动跳转登录页 |
| 删除最后一个 admin | 后端 `delete_user` / `update_user_role` 检查 admin 数量，最后一个 admin 不可删除/降级，返回 409 |
| 删除有文件的用户 | 后端 `delete_user` 检查用户名下文件，有文件则拒绝删除并返回文件列表，返回 409 |
| Admin 绕过所有权写文件 | Router 层 `can_write` 严格检查 owner，admin 无特权。Admin 需先 `change_file_owner` 接管后才可写 |
| 所有权变更中断编辑 | 所有权变更不影响当前编辑会话，当前编辑者继续持有锁直到主动释放或超时 |

## 拒绝的备选方案

1. **JWT 库方案**（Plan B 的 HMAC Token）：对 2-5 人团队过度工程化，增加依赖但无实际收益。自实现随机 token 存内存 dict 更简单。
2. **HMAC 签名 Token**（Plan B）：Token 无需签名，服务端内存存储足够安全。省去 HMAC 计算和密钥管理。
3. **`.perm.json` 单一集中式 `file_owners.json`**（原方案）：最初采用单一 JSON 文件管理所有文件权限，后改为用户要求的 per-file `.perm.json` 侧车文件，便于独立管理和迁移。
4. **Handler 内分散鉴权**（Plan A 提及但放弃）：30+ handler 逐个修改风险高。Router 集中拦截器是更优选择。
5. **Cookie 认证**：CLI/外部 API 使用不便，Token 方案更通用。
6. **CLI 用户管理工具**：改为 UI 管理界面 + REST API，提升用户体验和操作便捷性。
7. **REST API 触发配置热重载**：改为 watchdog 文件监听，减少 API 端点，简化实现。
8. **Admin 全能写模型**：原方案中 admin 始终可写。用户要求严格所有权模型——admin 需先接管文件才能写，无侧车文件全员只读。这确保了所有写操作都有明确的所有者追溯。
9. **import_file 覆盖模式**：原方案允许导入覆盖已有文件。用户要求仅允许创建新文件，避免覆盖时的所有权混乱。
10. **admin-only steal_lock**：原方案中 steal_lock 仅 admin 可执行。用户要求仅 owner 可执行，与严格所有权模型一致。
