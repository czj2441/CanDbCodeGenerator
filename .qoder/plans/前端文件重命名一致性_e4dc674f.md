# 前端文件重命名一致性调整

## 背景

前端经历了两次重大设计变更：
1. **动态报文标签页系统** (`c6a1f16`) — 固定三 Tab 导航替换为动态标签页
2. **底部面板/侧栏拖拽重构** (`43267e7`) — 底部面板选项卡化 + 侧栏拖拽缩放

变更后部分组件/Store 的实际职责已显著偏离其文件名。本方案进行两类调整：
- **A/B 类**（4 个文件）：职责已偏离文件名，需重命名
- **选项卡入口统一**（3 个文件）：统一三类选项卡入口文件的 `XxxTab` 命名格式，并删除过度封装的容器组件

## 文件职责分析

### 1. `MessagePanel.vue` (542 行) → 拆分为 `SignalPanel.vue` + `MessagePanel.vue`

**现状**: 一个文件包含三个互斥显示区域，信号属性（94行）+ 报文属性（48行）+ 空状态：

| 区域 | 触发条件 | 内容 | 模板行数 |
|------|---------|------|----------|
| 信号属性 | 有选中信号时 | name/start/length/byteOrder/factor/offset/min/max/unit/comment | L4–56 (52行) |
| 信号值描述 | 有选中信号时 | 值描述表引用选择器 + 内联条目编辑器（增删改）+ 新建值描述表 | L58–99 (42行) |
| 报文属性 | 无选中信号、有选中报文时 | id/name/dlc/cycleTime/isFd/sender/comment + 位使用率进度条 | L103–150 (48行) |

**拆分理由**: 信号属性和报文属性的表单逻辑完全独立，不存在共享的属性字段或编辑逻辑。即使信号和报文在数据模型上有隶属关系，它们的 property panel 之间没有共同特征，放在同一个文件里没有复用价值。

**拆分方案**:

| 文件 | 职责 | 变更类型 |
|------|------|----------|
| `SignalPanel.vue`（新文件） | 信号属性 + 信号值描述区域 | 从 MessagePanel 中提取 |
| `MessagePanel.vue`（保留原名） | 仅保留报文属性 + 空状态 | 删除信号相关代码 |
| `panel-styles.css`（新文件） | 共享基础样式（.panel / .field / .panel-section / .btn 等，约55行） | 从 MessagePanel scoped CSS 中提取 |

### 2. `SignalTable.vue` (589 行) → `SignalEditorTab.vue`

**原名暗示**: "信号表格"，暗示只是一个简单的数据表格。

**实际职责（完整的信号编辑视图）**:

| 功能模块 | 行数 | 描述 |
|---------|------|------|
| 标题栏 (center-header) | L3–9 | 显示当前报文名称、ID、信号数量 |
| 工具栏 (toolbar) | L11–32 | 添加信号、批量创建、批量编辑/删除、布局视图切换、列设置 |
| 数据表格 | L40–97 | 13列可排序表格，内联编辑，checkbox多选，双击进入编辑模式 |
| 键盘快捷键 | L315–361 | Ctrl+C/X/V/Z/A、Delete批量删除、Escape退出编辑 |
| 方向键导航 | L418–524 | ArrowUp/Down/Left/Right 单元格间导航，自动滚动到可视区域 |
| 列配置 + 排序 | L124–226 | 列定义、排序逻辑、列宽拖拽、列显隐设置 |
| 多选状态同步 | L228–236 | 与 uiStore 同步多选 keys，供右键菜单使用 |
| BatchEditModal 集成 | L102–105 | 批量编辑模态框 |
| Motorola/Intel 起始位转换 | L401–416 | displayStartBit ↔ storageStartBit 的双向转换逻辑 |

**为什么原名不够精确**: "Table"只描述了其中一个子功能（数据表格），但实际组件是一个**完整的编辑视图**，包含标题栏、工具栏、列设置、键盘交互、多选、排序等完整的编辑体验。

**新名 `SignalEditorTab` 的语义**: 作为信号编辑选项卡的入口文件，与 MessageTab、ValueTableTab 统一使用 `XxxTab` 后缀。内部承载表格/布局双视图切换。

**合并 SignalLayoutVisualizer 视图切换**:
- 原 MessageEditorTab.vue 的 `v-if="ui.layoutViewMode"` 切换逻辑合并到本组件内部
- SignalLayoutVisualizer 作为子组件导入，布局视图切换不再需要外部容器
- App.vue 只需 `<SignalEditorTab :msg-id="..." />` 一行

### 3. `editor.js` (558 行) → `coreStore.js`

**原名暗示**: "编辑器"store，暗示只管理编辑器相关的 UI 状态。

**实际职责（全局核心数据仓库，5 大职责域）**:

| 职责域 | 行数 | 具体内容 |
|-------|------|----------|
| 核心数据存储 | L14–24 | `messages`（报文列表）、`messageCache`（报文详情缓存）、`valueTables`（全局值描述表）、`busType`（总线类型） |
| WebSocket 连接管理 | L66–80, L157–228 | WS 连接建立/断开、健康检查定时器、WS 请求封装、连接超时等待 |
| WS 消息分发 | L233–507 | 处理 15 种消息类型：full_sync、signal_added/updated/deleted、message_added/updated/deleted、undo/redo_applied、value_table_*、data_errors_changed、lock_stolen、status_changed 等 |
| 会话生命周期 | L86–123 | 会话拆卸（6种 reason）、编辑器状态重置、标签页清理 |
| 运行时辅助 | L512–555 | 版本检查、API 健康检查、操作日志管理 |

**为什么原名不够精确**: "editor"暗示只是编辑器状态管理，但实际承担了：①全局数据唯一真相源 ②WS通信层 ③消息分发中心 ④会话管理 ⑤日志系统。它是整个前端应用的**核心数据枢纽**，被所有其他 store 和组件依赖（21 处 import）。

**新名 `coreStore` 的语义**: Core（核心）准确反映了它作为全局数据中枢的角色，`useCoreStore` 也清晰表明这是应用的核心 store。

**导出符号同步变更**:
- `useEditorStore` → `useCoreStore`（函数名，25 处调用）
- `defineStore('editor', {` → `defineStore('core', {`（Pinia ID，影响 DevTools 显示名）

### 4. `MessageEditorTab.vue` (17 行) → **删除**

**原职责**: 仅 3 行模板的视图切换容器：

**删除理由**: 17 行代码、零业务逻辑、仅在 App.vue 一处引用。其视图切换逻辑合并到 SignalEditorTab（原 SignalTable）内部，App.vue 只需 `<SignalEditorTab :msg-id="..." />` 一行。

### 5. 选项卡入口文件命名统一

**现状**: 三类选项卡的入口文件命名格式各不相同：

| 选项卡 | centerTab 值 | 当前入口文件 | 命名风格 |
|-------|-------------|------------|----------|
| 报文选项卡 | `'messages'` | `MessageTable.vue` | `{实体}Table`（UI 控件类型） |
| 值描述表选项卡 | `'valtables'` | `ValueTableList.vue` | `{实体}{UI控件}`（混合型） |
| 信号/动态报文选项卡 | `msg_{id}` | `MessageEditorTab.vue` | `{实体}Editor{角色}`（功能角色） |

**统一方案**: 全部使用 `{实体}Tab` 格式：

| 选项卡 | 新文件名 | 变更类型 |
|-------|---------|----------|
| 报文选项卡 | `MessageTab.vue` | 重命名（MessageTable → MessageTab） |
| 值描述表选项卡 | `ValueTableTab.vue` | 重命名（ValueTableList → ValueTableTab） |
| 信号/动态报文选项卡 | `SignalEditorTab.vue` | 重命名 + 合并布局视图切换（原 SignalTable + 原 MessageEditorTab 容器逻辑） |
